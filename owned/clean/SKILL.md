# Clean

按用户指定的范围清理注释与测试。未指定范围时，优先处理当前任务的改动及直接相关测试；不要顺带重构业务代码或扩展为全仓库清理。

## 注释

参考《Clean Code》的实践：注释只补充代码没能清楚表达的信息。

- 保留必要的意图、约束、取舍、外部约定和不明显的原因。
- 删除复述代码的注释、失效或误导的说明、日志式改动历史、作者与日期流水账、位置标记、无意义的分隔标题，以及已被版本控制保存的废弃代码。
- 有效的 TODO 应指向尚未解决的具体问题；不能仅因它记录了待办就删除。
- 保留许可证、必要的公共 API 文档和工具依赖的指令；删除前确认注释是否影响类型检查、lint、测试或代码生成。

## 测试

先核对行为约定、实现和现有测试，再判断每个用例实际能发现什么错误。

- 删除或合并覆盖相同行为、条件和失败模式的重复用例；仅名称、写法或数据不同，不代表覆盖不同。参数化确实能减少重复时才使用。
- 保留能发现不同错误的边界、异常、回归场景和必要的测试层次；不要仅凭执行了同一段代码或行覆盖率相同判断重复。
- 不准确的用例先按明确的行为约定修正。只有行为已废弃或等价覆盖仍然存在时才删除；实现违背约定时指出问题，不要改断言迎合错误实现。
- 清理同义反复测试：预期值直接来自实际结果、断言只重复测试自己的计算，或仅验证 mock 按自身配置返回而未检验被测行为。能改为独立预期值或可观察行为断言时优先改写。
- 删除用例时一并清理因此闲置的 fixture、helper 和 import；不要通过放宽断言、跳过测试或降低覆盖率门槛让检查通过。

## 验证与交付

运行与改动相关的测试及项目要求的检查。简要说明删除、合并或修正了什么，以及保留覆盖的依据；如无法运行检查，说明原因。
